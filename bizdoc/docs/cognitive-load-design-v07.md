# bizdoc v0.7「認知負荷ファースト」設計文書

対象: bizdoc プラグイン v0.2.1 → **v0.7.0**（plugin.json / marketplace.json 両方の version を上げる — キャッシュは version が変わらないと再取得されない。§11 Gotcha 準拠）。

確認済み前提: 現行 SKILL.md v0.2.1 全437行を読了（`bizdoc/skills/bizdoc/SKILL.md`）。統合した入力は5系統 — (1) 認知負荷トレンド調査（Grok・出典約30件）、(2) 動画的理解の学習科学調査（Grok・効果量つき）、(3) explainer 画像4枚 vs bizdoc B1 の画像差分実測（imgDiff）、(4) explainer 文書 vs bizdoc 出力の構造差分実測（storyDiff）、(5) Fable5 メタ認知（公理案と衝突裁定）。学術的裏付けは各調査の一次出典に依る（本文書では出典名のみ再掲）。

ユーザー制約の解釈（全設計に通底）:
- **クリーム色は不用** → ラスタ・SVG とも背景は純白 #FFFFFF 固定。禁止行で封じる。
- **情報を削るのではなく密度と表現を適切に** → 削る対象は extraneous（帳簿仕事: ナビ判断・開ループ保持・分割注意・冗長・装飾）だけ。情報そのものは削らず、波形整形・付録移動・図の分割で密度を適正化する。
- **流れるように** → 流れ = 読者の問い状態と文書の回答列の連続一致。破れ3種（早すぎる回答・遅すぎる回収・動機なき内容）を規範で塞ぐ。

## 1. 設計公理（7箇条）

各公理は「言い切り／裏付け／規範への写像」の3点セット。§3 の差分はすべてこの公理に遡れる。

### 公理1 読者状態契約 — 文書は読者の問いの発生順に並ぶ

位置 X の読者は X より上で確立したことしか知らない。まだ発生していない問いに答える節（早すぎる詳細）は置き場のない情報 = extraneous load になる。
**裏付け**: Conklin 1987（disorientation / cognitive overhead）、Mayer segmenting（学習者ペースの分節が連続提示に勝つ）、storyDiff 実測（A は前方参照 0 件、B は「（5章）」「別紙」参照 13 件で読線が切れた）。
**写像**: §3 D2（並び順の置換）・D8（前方参照禁止）・D10（読者演算禁止）。

### 公理2 問いは文書が起こし、回収は即時 — 各節の締めが次節の問いを開く

流れの破れは3つ: 早すぎる回答（F1）・遅すぎる回収（F2）・動機なき内容（F3）。動画が流れるのは「次を聞きたい状態」を作ってから次を言うから。主張が誘発する最強の反論は先送りせず直後の節で回収する。
**裏付け**: Rothkopf adjunct questions（挿入質問が標的記憶を上げる）、Minto 自身のピラミッド = 読者との Q&A 対話という定式化、storyDiff（A の目次7項は問い→回収の弧、B は「なぜ統合しないのか」を callout 1個に脚注化して弧を切った）。
**写像**: D2（question chaining の outline 検査）・D3（outline.json に `q` フィールド）。

### 公理3 見出し+lede は問いと答えの対 — 主張型を既定に、未解決要素を1つ残す

見出しは主張文（Assertion-Evidence）のまま維持する。ただし全見出しが「答えの言い切り」で完結すると、見出しを読んだ時点で本文を読む理由が消える。各見出しは本文が回収する未解決要素（なぜ／どうやって／何を捨てたか）を1つ残す。
**裏付け**: Garner et al. 2013（n=110・主張文+視覚証拠で理解↑誤解↓主観負荷↓遅延再生↑。入力5系統中で最も強い実験根拠）、storyDiff（A の見出しは「役割ラベル — 緊張を残す主張」、B の言い切り型は本文を証拠の付録に落とした）。
**写像**: D4。**問い型見出しへの全面転換は不採用**（理由は §7 裁定1）。

### 公理4 exec-summary は地図であって荷物ではない — what を言い切り、why/how を開けておく

冒頭要約は判断文（BLUF）であって abstract ではない。各項目に本文でしか解けない緊張語を1つ残す（例:「品質を**守りながら** 42% 削る」）。補足を冒頭に積むと本文に閉じるループが残らず流れが死ぬ。
**裏付け**: AR 25-50（焦点あるメッセージを即時に送れないことが文書の最大の弱点）、spoiler 研究（説明型ではネタバレが処理流暢性を上げる・高確度）、bizdoc 実測（全項目に補足を付けた exec-summary は 576字 = explainer TL;DR の 2.8倍で文書中最重ブロック化）。
**写像**: D7。既存の予算規範（3項目・各1文）は不変のまま認知的根拠を得る。

### 公理5 図=入口、本文=記録 — 構造は図が先に見せ、本文は図をなぞって語る

構造（対比・流れ・関係）を主張する節は図を節頭に置き、本文は図中ラベルをそのままの語で主語に使って図を歩く。図の説得力は図形量ではなく言語・数値の錨（ラベル・副ラベル・実データ標本・判定マーク）が作る。要点が図にしかない状態は引き続き禁止（検索・選択・読み上げの正本は本文）。
**裏付け**: 空間近接のメタ分析（Ginns 2006, d=0.85 — 入力中最大の効果量）、multimedia principle、imgDiff 実測（B1 はアイコン・矢印の図形量では explainer と同水準なのに日本語ラベル 5 vs 14〜21・数値トークン 0 vs 5〜35 で決定的に負けた）、storyDiff（A の最初の視覚要素は Before/After 構造図、B は KPI カード3枚で桁の物語の再構成を読者に負わせた）。
**写像**: D9（役割固定・初手構造図）・D16（B2 spec）・D19（figcaption ナレーション）・D22（Gotcha 置換）・§5 全体。

### 公理6 密度は波形 — 情報は削らず、到着レートを整形する

外在負荷を削って空いた作業記憶は「予測→確認」（germane load）に投資する。節内は フレーム1行 → 図（構造）→ 本文（因果）→ 密度の山（表・コード・複雑図）→ 回収1行 のリズムで、山は1節1つまで。900px ごとの視覚要素の床は不変。
**裏付け**: CLT の現在形（germane は足す対象ではなく、外在を削って空いた容量が理解になる — Kim 2025）、動画の「1カット=1変化」= segmenting の実装、storyDiff（B は kpi-grid 直後に table と同役ブロックが連続し本文がキャプション役に落ちた）。
**写像**: D5（1画面=1ビート）・D6（波形）・D14（redundancy と再掲のスコープ）。

### 公理7 決裁はレイヤー、理解が基盤 — 入口と出口だけを差し替える

理解していない決裁者は遅く・誤って承認する。決裁は文書終端の speech-act であり、本文の流れ構造（公理1〜6）は共有する。決裁レイヤーが差し替えるのは exec-summary への依頼1項目と終端の判断材料ブロックだけ。手続き情報（宛先・版数・機密表示・承認事項・期限）は本文へ浸潤させない。
**裏付け**: Dykes 2026 の 2×2（低抵抗×低複雑の1象限だけがピラミッド最適 — 構成の弧は抵抗で切り替える）、storyDiff（B は手続きが lede・exec-summary・callout に浸潤し、手続きで文書が終わる。A は結論ブロックで冒頭の約束を回収して環を閉じた）。
**写像**: §2 モード設計・D1・D12・D13。

## 2. モード設計 — 既定=理解優先 / opt-in=決裁レイヤー

新しいモード分岐フラグは作らない。**Phase 0 の既存項目「目的」に承認・決裁・予算獲得が含まれるとき決裁レイヤー on**（種別=提案書だから on、という機械分けはしない。報告書でも決裁を含み得る）。

### 不変（公理層 — 両モード共通）

| 不変原則 | 由来 |
|---|---|
| 読者状態契約（問いの発生順・前方参照禁止・読者演算禁止） | 公理1 |
| question chaining（節の締めが次節の問いを開く・反論は直後回収） | 公理2 |
| 見出し=主張+未解決要素1つ、骨格可読性 | 公理3 |
| exec-summary 3項目各1文+緊張語、ピラミッド会計（各結論に支持節） | 公理4 |
| 図=入口・本文=記録、視覚要素の役割固定、figcaption ナレーション | 公理5 |
| 密度の床（900px）と波形（1節1山）、表セル40字・4列 | 公理6 |
| 出典規律（数字に出典・節末1本に集約）、redundancy 禁止 | 既存+D20 |
| 末尾の結論ブロック（exec-summary の各項を1行ずつ回収して環を閉じる） | D12 |

### 可変（決裁レイヤー on で追加・切替）

| 部位 | 理解優先モード（既定） | 決裁レイヤー on |
|---|---|---|
| exec-summary | 結論3項目のみ | +依頼事項1項目（何をいつ承認してほしいか。1文） |
| 文書終端 | 結論ブロックで終了 | 判断材料ブロック（金額・リスク・ゲート・切戻し）→ 承認事項・添付一覧 → 結論ブロック の順 |
| `.cover` meta | 日付・読者・種別 | +宛先・版数・機密表示（meta 行に隔離。lede には書かない） |
| `.sec-lede` | 反直観の核1行 | 二重契約: 逐次読者への半歩先スポイラー + 途中参入者への「この節の問いと答え」局所復元（決裁者はジャンプインする） |
| 推奨の位置（抵抗軸） | 低抵抗: exec-summary で推奨まで言い切る | 高抵抗・対立案件: exec-summary は「何が分かったか」（発見）に留め、推奨は証拠の後 = 終端の判断材料ブロックで出す（Minto の例外 / Dykes 2×2。ただし1枚文書なので3画面以内で洞察に着地） |

## 3. SKILL.md への具体的な規範差分

各差分は【置換】（現行文を書き換える）/【追加】（新設）を明記。アンカーは現行 SKILL.md の実テキスト。

### Phase 0（§4）

**D1【追加】** 4項目リストの直後に:

> 5. **決裁レイヤー判定**: 目的に「承認を得る・決裁を仰ぐ・予算を獲得する」が含まれるか。含まれれば決裁レイヤー on（exec-summary への依頼1項目・終端の判断材料ブロック・cover meta の宛先/版数。本文の構成規範は変えない）。含まれなければ理解優先の既定構成のみ。あわせて**読者の抵抗**を判定する: 結論が読者の既存方針・利害と対立する題材なら高抵抗とし、exec-summary の項目を「発見」に留めて推奨を終端の判断材料ブロックへ置く（§2 可変表の抵抗軸）。

### Phase 2（§6）— 構成規範

**D2【置換】** 現行:

> `blocks` の並び順はこの文書にとって自然な流れを都度考えて決める（固定順は持たない）。

新:

> `blocks` の並びは主題の分類でなく**読者の問いの発生順**で決める（固定順は持たない）。位置 X の読者は X より上で確立したことしか知らない前提で書く。outline 段階で次の2つを検査する:
> 1. **question chaining 検査**: 各節が末尾に残す問いを1行ずつ書き出し（outline.json の `q`）、次節の見出しがその問いを受けているか確認する。受けない節は並べ替えるか接続文を足す
> 2. **反論の即時回収**: 主張が誘発する最強の反論（「なぜもっと安い案にしないのか」等）は評価章へ先送りせず、その主張の直後に専用の節を立てて回収する

**D3【置換】** outline.json の形。現行 schema に `q` と `budget` を追加した現物:

```json
{
  "slug": "kebab-case-slug",
  "type": "提案書",
  "approval_layer": false,
  "budget": { "sections": 6, "figures": 4, "raster": 1 },
  "cover": { "title": "...", "date": "2026-08-20", "purpose": "...", "reader": "..." },
  "exec_summary": {
    "why": "...",
    "points": ["...（各項目に本文でしか解けない緊張語を1つ残す）"],
    "request": "決裁レイヤー on のときだけ: 何をいつ承認してほしいか1文"
  },
  "blocks": [
    {
      "purpose_key": "根拠・数値を示す",
      "expression": "kpi-grid",
      "why": "<この目的・読者にどう効くか1行>",
      "q": "<この節が回収する読者の問い（前節が開いたもの）1行>",
      "opens": "<この節の締めが次節へ開く問い1行。最終節は空でよい>",
      "content": { "...": "..." }
    }
  ]
}
```

> `budget` は器の予算（節数・図の枚数）を生成前に宣言するもの。超過したときは**情報を削らない** — extraneous（冗長・帳簿仕事・装飾）を削るか、情報を付録へ移すか、図を分割する（AI 生成文書は放置すると verbosity 側に膨らむため、予算は「足す」でなく「移す・整形する」編集を強制する装置）。

**D4【追加】** 見出しレジスター規範（「用言で言い切る」の項の後）に:

> - **未解決要素を1つ残す**: 見出しは主張文のまま、本文が回収する未解決要素（なぜ／どうやって／何を捨てたか）を1つ残す。目次を上から読んだとき全見出しが「答えの言い切り」で完結している outline は差し戻す（見出しを読んだ時点で本文を読む理由が消える）
> - **疑問形の条件付き許可**: 読者が自発的に抱かない問いを文書側が起こす必要がある節に限り、疑問形見出し（「なぜ〜のか」— 用言終止として合法）を使ってよい。その場合 `.sec-lede` に1行の答えを必ず置く。1文書1〜2節まで。トピックラベル・答えの伴わない問いは引き続き禁止
> - **骨格可読性**: 見出し＋sec-lede だけの拾い読みで文書の論旨が再構成できること（Phase 5 の検査項目）

（**問い型見出しへの全面転換は不採用**。主張文+視覚証拠の Garner 2013 が入力中最強の実験根拠であり、手本にした explainer 現物でも問い型は7節中1節のみ。全面転換は AE の利得を捨てる。詳細は本設計文書 §7 裁定1）

**D5【追加】**「1セクション = 1メッセージ」の項に追補:

> **1画面 = 1ビート**: 各節はおおよそ1ビューポート（900px 目安）を1ビートとし、節の完了条件（この画面を読んだら読者が言えること）を1つだけ持つ。2つ言えるなら節を分割する。同一画面に新しい用語・新しい因果・例外を同時に出さない（例外・注記は次ビートか付録へ）

**D6【置換】** 現行:

> - **密度規範**: スクロール1画面（目安 900px）ごとに視覚要素（図・表・カード・KPI）を最低1つ置く。ベタ段落だけのセクションを作らない

新:

> - **密度規範（床と波形）**: スクロール1画面（目安 900px）ごとに視覚要素（図・表・カード・KPI）を最低1つ置き、ベタ段落だけのセクションを作らない（床・現行どおり）。加えて**密度の山は1節1つまで**とし、高密度要素（表・コード・複雑図）の直前に1行のフレーム（何を見るか）、直後に1行の回収（「つまり〜」）を置く。情報を削って密度を下げるのではなく、到着レートを波形で整形する

**D7【追加】** 冒頭要約の予算（配置規範）に追補:

> - **緊張語**: `.exec-summary` の各項目には本文でしか解けない緊張語を1つ残す（「品質を**守りながら** 42% 削る」の“守りながら”）。項目は「何をどうするから何が起きる＋実測値1つ」の因果文で書き、状態宣言（「〜は特定済み」）・スケジュール約束を置かない（手続きは終端へ）
> - **lede は理解の約束**: `.lede` には「この文書を読むと何が分かるか」の約束1文と鍵となる洞察の予告1句を置く。決裁文書でも承認依頼は1句に留める（「実施承認をお願いするものです」型の手続き宣言だけの lede を禁止）

**D8【追加】** 構成規範に新設:

> - **前方参照禁止・証拠はその場**: 「詳細は後述」「（N章）」「（別紙N）」のみを根拠として表セル・本文に置くことを禁止する。品質・効果の主張には、その場で最小の裏どり（実測値1つ＋確認手段1語）を添える。集約評価の節は置いてよいが、証拠の初出の場にしない

**D9【追加】** 構成規範に新設:

> - **視覚要素の役割固定**: 図=構造、表=数値比較、callout=判定・洞察（「この表の下2行が設計の芯」）と役割を分け、同役ブロックの連続（kpi-grid 直後の table 等）を禁じる。callout はセクション末の判定・洞察専用スロットとし、コンプライアンス注記・手続き連絡を置かない
> - **初手は構造図**: 文書の最初の視覚要素は数値カード群でなく構造図（Before/After・全体像）にする。kpi-grid は読者が構造モデルを得た後の効果まとめ・実績報告に限る。新出概念が3つ以上ある文書は、最初の構造図を「登場概念のラベル付き地図」を兼ねる形にし、専門用語の初出を図中ラベルと同時にする（本文だけで定義しない）

**D10【追加】** 構成規範に新設:

> - **読者に演算・照合をさせない**: 同一事実は1つの単位系で示し、換算・検算（増加率の積・円換算等）は書き手が済ませて結果だけ添える。番号参照（「施策②」等）は定義の後にのみ使う。表・図・終端に出る語の初出には1句の説明を付ける

**D11【追加】** 構成規範に新設:

> - **短い呼び名**: 反復参照される系・コンポーネント・施策が2つ以上あるときは、初出（できれば表の先頭列）で短い呼び名（A/B・①②③等）を与え、以後それで通す。字面の似た長い複合名を無短縮で反復しない

**D12【追加】** 構成規範に新設:

> - **手続き隔離と結論ブロック**: 手続き情報（機密表示・宛先・版数・承認事項・添付一覧・期限約束）は `.cover` の meta 行と終端の2箇所に隔離し、exec-summary・sec-lede・callout に混ぜない。文書末尾には exec-summary の各項を1行ずつ回収する**結論ブロック**を置き、手続き・残課題で文書を終えない（承認節・残課題節の後に結論を置く）

## 4. 画像 spec B2 の確定版

### 採用: B案（白地・高密度・クリーンフラット）。手描きタッチは不採用

理由:
1. **フォーマル整合**: bizdoc は関係部署に展開する業務文書。現行 B1 spec 自身が「手描きマーカーの質感にしない」「手描きの乱れた線」を禁止しており、手描き解禁は文書全体のレジスターと衝突する。B案は既存トーンとの連続性が高く、白基調 HTML に並べたときの馴染みで優る
2. **密度と手描きは独立変数（実測）**: imgDiff で最高密度だった concept-01（ラベル約20・数値約35）は白地であり、手描き=スタイル変数・密度=機構という分離が実測で立っている。explainer らしさの正体は密度機構であって手描きではない

## 5. SVG / drawio 図への密度規範（svg-patterns/README.md 予防則11〜15 として新設）

explainer 画像の密度機構のうち、ベクタ図に移植するのは次の5つ。**移植しないもの**: 下段テイクアウェイ帯（SVG では figcaption がその役割を担う — 帯を図内に持つと1図1主張と幅制約に衝突する）、決め数値バッジ（文書側の kpi-grid / callout が担う。図内に置くなら1図1個まで）。

> **予防則11 — 無名の箱を描かない**: 図中の主要ボックスには「名詞＋数値」の副ラベルを付ける（「要約系 4回」「候補 3件」）。数値を持たない要素は、統合するか、そもそも描く必要があるか見直す。副ラベル追加で viewBox 幅が予防則9 の上限を超えるなら図を分割する（1図1主張は不変 — 密度は1つの主張を支えるラベル・数値の密度であり、主張の数ではない）
>
> **予防則12 — 読み順と終端**: 流れ系パターン（process-flow・手順・状態遷移）は読み順を丸数字①②③…で明示する。流れの終端には ✓（到達・解決）か ✗（未達・問題）を置き、宙に浮く矢印を残さない
>
> **予防則13 — 実データ標本**: 設定値・パス・環境変数・係数は抽象記号に置き換えず、実物の文字列を `font-family: ui-monospace, monospace` で一字一句正確に描く。強調は該当部分文字列だけをアクセント色の点線枠で囲む（読者が図を信じる根拠を図の中で渡す）
>
> **予防則14 — 反復は個数で見せる**: 「N回・N件」が主張そのものなら、同一図形を実際に N 個並べる（数量の反復描画が証拠になる）。N が 9 を超えるときは代表数個＋「×N」表記に切り替える（要素数と幅の制約が勝つ）
>
> **予防則15 — 強調は同時1点**: accent 色・矢印・点線枠による強調は1図あたり同時1点まで（3点以上光らせると合図が消える — signaling は稀少資源）。複数箇所を強調したい図は分割するか、番号順路（予防則12）で時間差をつける

drawio（Mermaid 経由）への適用: ノードラベルに副ラベルを併記（`A["要約系<br/>4回"]`）、edge label で判定を書く（`-->|✓ 到達|`）、読み順は番号をラベルに埋める。drawio-bridge の `inlineSvg` 整形・accent 寄せは現行どおり。

HTML 側との接続（公理5）: 図中ラベルの語彙 = 本文の主語群（言い換え禁止）。figcaption は図の主張1文のナレーション（D19）。これにより「図を読む→同じ語で本文が歩く」の往復ゼロ導線が成立する。

## 6. 検証設計 — ブラインド審査

### 目的と構え

v0.7 の規範は explainer との差分分析**から**導出した。同じ題材で勝つだけでは過適合の証明にしかならない（self-improvement-integrity）。よって**2題材×3アーム**で走らせる。

- **題材1（継続性）**: Bedrock 通話解析の費用最適化（規範導出に使った題材。ここで負けたら設計が誤り）
- **題材2（汎化）**: 規範導出に使っていない未使用ドメインの実題材1本（例: 社内ツール導入提案・障害報告など、実データが手元にあるもの。審査前に固定する）
- **アーム**: (A) bizdoc v0.7 / (B) run-explainer-page / (C) bizdoc v0.2.1（退行検査）

### ブラインド化

- 審査用コピーを作り、生成元が分かる表記（kicker の種別ラベル差・footer の生成情報・hub ナビ）を除去、アクセント色を3アームで統一、ファイル名は乱数ラベル
- 審査員は**会話履歴なしの新セッション×3**（Claude / Codex / Grok — evaluator-gate の資産を再利用。fresh evaluator の教訓: 制作文脈を持つ審査員は甘くなる）
- 審査プロンプトに v0.7 の規範を漏らさない（規範遵守チェックにすり替わると、規範自体の妥当性が測れない）

### 機械検査（審査前ゲート — 落ちたら審査に出さず作り直す）

前方参照（`後述|（N章）|別紙`）0件 / ※出典行が節あたり1本以内 / td 40字・4列以内 / 見出し35字以内 / exec-summary 3項目・全文300字以内 / 目次5節以上で存在。数値の集計はいずれも独立レーンで再導出してから確定する（verification-integrity R5/R6）。

### 審査観点5つ

1. **牽引（流れ）**: 各節を読み終えた時点で次節を読みたい理由が立っているか。見出し＋導入行だけの拾い読みで「先を読む問い」が残るか
2. **認知負荷（往復の少なさ）**: 読み返し・前方参照・単位換算・用語の再マップを何回強いられたか（回数を数えて報告させる）
3. **要点再生**: 30秒スキム→文書を閉じて「要点3つ＋決め数値1つ」を再生→原文と照合（誤解・欠落の数）
4. **図の伝達力**: 図が節の構造を本文より先に渡しているか。図の副ラベル・数値・判定が主張を自立して支えているか（無名の箱・名詞だけのキャプションの有無）
5. **業務文書としての即用性**: この文書だけで意思決定・報告・引き継ぎがそのまま実行できるか（判断材料・出典・手続きの完備と、本筋への非浸潤）

### 審査プロンプト骨子

```
あなたは業務文書の審査員。添付の3文書（X/Y/Z・同一題材）を読み、以下を報告する。
制作経緯・生成手段は知らされていない。推測もしない。内容の正しさではなく「読者としての体験」を測る。

手順:
1. まず X を30秒だけスキムして閉じ、要点3つと決め数値1つを書き出す。Y・Z も同様
2. 次に各文書を通読し、読み返し・別節参照・換算を強いられた箇所を回数つきで記録する
3. 観点1〜5（牽引/往復の少なさ/要点再生/図の伝達力/即用性）を各10点で採点し、根拠を各2文で書く
4. 最後に「関係部署に展開する1通を選ぶなら」を強制択一し、理由を3文で書く

禁止: 引き分け判定。装飾・見た目の好みを根拠にすること。文書間のスコア調整（各文書を独立に採点してから比較する）。
```

### 勝利条件と扱い

- **採用**: 総合強制択一で v0.7 が 2題材とも 2/3 以上、かつ観点別で v0.2.1 に全敗する観点がない（退行なし）
- **部分採用**: 題材1のみ勝ち → 過適合を疑い、負けた題材の審査根拠から規範を1つずつ外して再走
- **不採用**: explainer に総合で負け → 公理は保持し §3 の差分を見直す（deep-research が汎用スキルに 2-0 で敗北して一本化した前例に従い、結果を尊重する）
